# Data Model: Correct & Secure Service-to-Service Integration (018)

This feature is **corrections + transport**; it introduces almost no new persistent state. The spec's
key entities are mostly configuration and in-flight constructs. Where each lives is called out.

## Orchestrated Call *(in-flight, not persisted)*

One back-office action's request to an owning service.

- **Fields**: target service, HTTP method + path, request body (receiver's real shape), derived values
  it must supply, idempotency key, expected success response mapping, error→outcome mapping.
- **Source of truth**: the `Http*Adapter` methods + the receiver's request/response DTO records.
- **Validation**: body must bind + Bean-Validate against the receiver's real request record (Decision 2).
- **Outcome mapping**: 2xx/409 → applied; receiver 4xx (business) → REJECTED_INVALID (422) with the
  receiver's reason; receiver 403 → REJECTED_NOT_PERMITTED (403); 5xx / TLS / handshake / timeout →
  FAILED_UNAVAILABLE (503, retryable). The action's result is still recorded in the existing
  `back_office_activity` (append-only) — unchanged by this feature (FR-010).

## Integration Contract *(build-time artifact, not persisted)*

The agreement between a calling and a receiving service that the automated checks verify.

- **Fields**: port method ↔ receiver endpoint, request record, response record, required/derived fields.
- **Representation**: the receiver's real DTO records (added as `testImplementation` deps) + the
  consumer-contract tests that bind against them + the coverage/registry guard listing every port method.
- **Invariant**: every `*Port` method has a contract test; a field renamed on either side fails the build
  (SC-003); the `InMemory*Adapter` fakes satisfy the same contract (FR-006).

## Service Identity *(credential, never in the repo)*

The credential a service presents to prove which service it is.

- **Fields**: subject/CN = service name, SAN = docker service name, issuer = dev CA, `notBefore`,
  `notAfter`, key pair.
- **Storage**: PKCS12/PEM bundle in a Docker volume / gitignored path, generated by the cert-bootstrap
  step; referenced by a Spring Boot SSL bundle. **Never** committed, in tfvars, or logged (FR-011).
- **Lifecycle**: issued by the CA at bootstrap; rotated by replacing the mounted files (Boot reloads via
  `reload-on-update`, FR-009); validity observable via `management.health.ssl` before expiry.
- **Trust**: each service trusts the CA (truststore); TLS uses **`client-auth: want`** so the request
  reaches the app, where a mandatory `ServiceIdentityFilter` verifies the peer cert against the **service
  allowlist** and refuses (recording — see Refusal Record) any caller it cannot verify. `want` (not `need`)
  is chosen precisely so a no-cert caller can be *recorded*, not silently dropped at the handshake
  (research Decision 3).

## Refusal Record *(persisted — clarified 2026-07-23)*

A durable, queryable row written by the receiving service's `ServiceIdentityFilter` when it refuses a
caller for an identity/transport reason — so an intrusion attempt is auditable after the fact (FR-008).

- **Table**: `service_call_refusal` in **each receiving service's own schema** (schema-per-service; the 5
  backend services all receive internal calls). No shared library — the small filter + Flyway migration is
  added per service, consistent with KITA's one-module-per-service convention.
- **Fields**: `id` (UUID, `@UuidGenerator`), `occurred_at` (timestamptz), `peer_address` (text),
  `attempted_cn` (text, nullable — null when no cert presented), `reason` (enum:
  `NO_CERT|UNTRUSTED_CA|EXPIRED|NOT_ALLOWLISTED`), `request_path` (text), `request_method` (text).
- **Write path**: the filter persists in a short `REQUIRES_NEW` transaction, then returns 401/403 — the
  refusal is recorded even though the request never reaches a controller.
- **Distinct from**: a business rejection (422, has a business reason) and an actor-permission refusal
  (403 from the receiver's own `require(Role)`); this is a *service-identity* refusal.
- **Retention/query**: queryable by operators; no UI in this feature (out of scope) — a raw
  read/endpoint may follow later.

## Derived Value *(in-flight, deterministic)*

A value a receiver requires that no human supplies, produced by the caller so retries stay idempotent.

- **Examples**: `locationId` (default/primary location, looked up from operations), item ref→UUID
  (operations catalog lookup), `supplierCode` (deterministic slug of the supplier name), `poNo`
  (omitted — receiver generates).
- **Invariant (FR-002)**: same action inputs → same derived value, so a retried call (with its stable
  `X-Idempotency-Key`, 409-as-applied) never produces a second record.

## State & transitions

No new state machine. Existing lifecycles are unchanged (operations sales order, procurement PO,
`back_office_activity` outcomes). The only new transition is at the transport layer: a call either
completes over mTLS (verified peer) or is refused by the `ServiceIdentityFilter` and written as a Refusal
Record (FR-008) — never a business outcome.

## Persistence changes

**One new table per receiving service**: `service_call_refusal` (above), added via a Flyway migration in
each of the 5 backend services' schemas — the minimum the clarified FR-008 (persisted, queryable refusals)
requires. No changes to any existing table, and no change to the `back_office_activity` audit (FR-010).
The orchestrated-call corrections (US1) remain migration-free.
